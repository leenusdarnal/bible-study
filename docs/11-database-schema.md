# 11. Database Schema Proposal

- **Status:** Proposed physical design; migrations 0001–0004 apply in local D1 CI with core integrity and mapping-group checks; preview and production validation remain open.
- **Target:** Cloudflare D1 (SQLite) + Drizzle ORM.
- **Related:** [Data model](04-data-model.md), [Architecture](03-technical-architecture.md), [ADR-005](../decisions/ADR-005-database-schema.md), [Reading Progress specification](22-reading-progress-tracker-spec.md).

This is a design specification, not an executed migration. Implement in slices and validate against the actual D1 runtime before production use.

## 11.1 Physical design rules

1. Use stable text IDs (UUIDv7 or UUIDv4 generated by the application) for durable records. Never expose rowids as identity.
2. Use INTEGER for booleans, counts and UTC Unix epoch milliseconds; TEXT for IDs, codes, labels and URLs. Choose one timestamp representation consistently.
3. Use explicit foreign keys, NOT NULL, UNIQUE, CHECK constraints and composite indexes. Verify foreign-key enforcement in the deployed D1 environment.
4. Default to RESTRICT for published knowledge and source records. Use CASCADE only for genuinely dependent rows.
5. Retire published records instead of silently deleting them. Preserve source and editorial history.
6. Keep large files, scans, images, audio and import archives in R2. D1 stores structured data, metadata and R2 object keys.
7. Avoid unenforceable polymorphic foreign keys for core relationships. Prefer typed join tables.
8. Store flexible metadata as validated JSON text only where fields are genuinely variable; frequently filtered data belongs in columns.
9. Keep public knowledge separate from private user data. Enforce ownership and roles on the server.
10. Imports and publication must be idempotent, auditable and recoverable.

Common fields for applicable editorial records: id, status, created_at, updated_at, created_by, published_at. Do not add them mechanically to every join or immutable snapshot table.

## 11.2 Scripture identity and translations

Separate four concepts:
- **Scriptural work:** identity of a biblical book, independent of canon order.
- **Canon:** the collection and ordering of books.
- **Versification scheme:** chapter and verse units and numbering.
- **Translation edition:** a particular text edition that uses a specified scheme.

A printed reference such as Psalm 3:1 is not a globally unique identity.

| Table | Key columns and purpose |
|---|---|

| canons | id PK, code UNIQUE, name, tradition_label, description, status |
| canon_books | id PK, canon_id FK, work_id FK, position, display_name, is_included; UNIQUE(canon_id, work_id), UNIQUE(canon_id, position) |

| scripture_units | id PK, scheme_id FK, work_id FK, chapter_id FK, unit_label, unit_order, unit_kind; normally a verse |
| scripture_mapping_groups | id PK, from_scheme_id FK, to_scheme_id FK, group_type, source provenance, confidence, review_status, rationale |
| scripture_mapping_group_members | id PK, mapping_group_id FK, side, scheme_id FK, unit_id FK, member_order; ordered source and target unit sets |

| translation_editions | id PK, code, name, abbreviation, language_tag, publisher, edition_label, publication_year, versification_scheme_id FK, licence_id FK, rights_status, source_id FK, status |

Mapping groups are the canonical representation of a reviewed relationship between two versification schemes. Ordered group members explicitly capture the source-side and target-side unit sets, supporting one-to-one, one-to-many, many-to-one, many-to-many (for example, three source units to two target units), moved, subverse and absent relationships. Pairwise scripture_unit_mappings rows are optional edges within a group and are constrained to use group-member endpoints. Legacy pairwise rows remain valid with a null mapping_group_id. Translation text is attached to a unit in the edition's own scheme. The first release can seed one primary Protestant scheme and the 66-book canon without assuming all future editions use identical divisions.

### Versification mapping groups\n\nA mapping group links exactly two distinct versification schemes. Its ordered members are divided into from-side and to-side sets, and every member is constrained to a Scripture unit in the corresponding scheme. A group can contain multiple members on either side; an absent mapping can have members on only one side. Optional pairwise mapping edges must connect members of that same group. Do not approve a group until the source profiles, exact unit sets, source citation, rationale and reviewer decision are recorded. Migration 0004 adds this structure and preserves existing pairwise mappings as ungrouped rows.\n\n### Passage references

Use passage_references (id, label, reference_scheme_id, created_at) and passage_reference_segments (id, passage_reference_id, segment_order, start_unit_id, end_unit_id, notes).

A continuous passage has one segment. Non-contiguous passages have multiple ordered segments. Validate that endpoints belong to the declared scheme and that ranges are valid. A segment may cross chapters but should not cross books unless the reference parser explicitly models that case. Do not use free-text references as join keys.

Canon membership/order is separate from numbering. A scheme may define units for a work not included in a particular canon; canon-specific reference validation must check membership.

A source is the bibliographic work or dataset; a source_version is a specific edition/download/snapshot; a citation is the exact location in that version. This separation prevents a bare URL from being treated as sufficient evidence. Evidence relations should distinguish supports, challenges, contextualises and mentions. Evidence strength describes source/evidence quality, not theological truth.

Do not store copyrighted source excerpts unless the licence or permission allows it. A locator and attribution may be sufficient.

**Reading progress integrity rules:**
- Cloud trackers belong to a verified account. Guest trackers live in IndexedDB; installation IDs do not authenticate users.
- Every tracker declares canon, scheme and scope mode (all_books or selected_books).
- Selected-book rows must reference works in the tracker's canon; selected scope cannot be empty. Create a selected-books tracker by inserting the base row in all-books mode, adding one or more selected book rows, then switching scope to selected-books in the same transaction. The triggers prevent direct empty selected-scope insertion, empty scope activation, deleting the final selected book or moving the final selected book to another tracker.
- Chapter progress references stable scheme_chapters IDs. Composite foreign keys validate the tracker's scheme, canon and chapter work; triggers validate the selected-book scope on insert and on progress edits. Services still enforce owner access and validate the complete operation.
- No progress row means unread. Stored states are in_progress or read. A read state requires completed_at.
- Overall percentages and book states are derived, not stored counters.
- Reading plans and chapter completion are separate.
- Guest-to-account migration is explicit and idempotent. Multi-device sync needs mutation IDs, tombstones and conflict rules.

The legacy user_reading_progress proposal is superseded by these tracker tables. Draft DDL and selected-scope triggers are in [0003_reading_progress.sql](sql/0003_reading_progress.sql). SQLite regression tests are in [test_reading_progress_migration.py](../tests/sqlite/test_reading_progress_migration.py). Do not create both models for the same chapter-completion purpose. If plan-step completion is needed, add a separately named table.

Every private library operation must enforce user ownership on the server. Notes, bookmarks and highlights reference stable passage identities, not copied translation text. Offline sync should be a later migration with explicit conflict rules.

## 11.9 Index and integrity plan

Plan indexes for:
- scripture_units by (scheme_id, work_id, chapter_id, unit_order) and reference labels;
- translation_texts unique (edition_id, scripture_unit_id);
- mappings by both from_unit_id and to_unit_id;
- canon_books unique (canon_id, work_id) and (canon_id, position);
- entity_names by normalised name/language and entity_id;
- entity_external_ids unique (dataset_id, external_id);
- entity_relationships by subject/type and object/type;
- entity_passages by entity_id and passage_reference_id;
- evidence by relationship_id and claim_id;
- citations by source_id/source_version_id;
- content by editorial status/publication date and revisions by content/revision number;
- user-owned records by user_id and relevant updated/last-read timestamps;
- reading_tracker_chapter_progress unique (tracker_id, chapter_id);
- reading_tracker_books unique (tracker_id, work_id);
- staged records by import_run_id/validation_status.

Service and integration rules:
- Validate passage endpoints, translation units, relationship types and evidence targets.
- Users cannot access another user's private records.
- Tracker chapter rows must belong to the tracker's scheme, canon and selected scope.
- A selected-book tracker must have at least one selected book.
- Percentages are derived; never trust client-submitted counters.
- Published claims/content require reviewed citations and permissions.
- Preserve source and editorial history.

## 11.10 Incremental migration plan

**Slice A — Scripture foundation:** scriptural works, canons, canon membership, versification schemes, chapters, units, mappings, translation editions/texts and passage references.

**Slice B — Public study and encyclopedia:** entities, names, external IDs, initial specialised entity tables, relationship types/edges/evidence, content and passage/entity links.

**Slice C — Evidence and editorial:** sources, versions, licences, citations, claims/evidence, contributions, reviews, audit, chronology/geography and textual criticism as required.

**Slice D — Personal library:** auth integration, profiles, roles, preferences, notes, bookmarks, highlights, reading plans, reading trackers and chapter progress.

**Slice E — Import/search scale:** datasets, versions, runs, staging, merge history, search projection and later offline sync.
